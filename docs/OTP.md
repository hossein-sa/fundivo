# Fundivo — OTP Authentication (Phase 1, Part 2)

Implemented: `POST /api/v1/auth/otp/request/` and `POST /api/v1/auth/otp/verify/`.

**This is not a completed login flow.** Verification returns a short-lived **login ticket**, not a JWT and not an authenticated session. The following phase will exchange that ticket for JWTs using a single atomic GETDEL operation. Until that step is implemented, do not claim users can sign in to protected endpoints.

## Public API

Both endpoints allow anonymous POST requests and accept JSON. The validation error is `400` for malformed input. `429` means an OTP rate limit has been reached. `503` means the Redis or delivery backend is unavailable.

### Request

`POST /api/v1/auth/otp/request/`

```json
{"phone_number": "09123456789"}
```

`202 Accepted`:

```json
{"detail": "If delivery is available, a code has been sent."}
```

This response is identical for an existing or new phone number. Repeated requests during cooldown do not send a new code. The API does not disclose the OTP.

### Verify

`POST /api/v1/auth/otp/verify/`

```json
{"phone_number": "09123456789", "code": "123456"}
```

`200 OK` (example fields, ticket value intentionally redacted):

```json
{"login_ticket": "<one-time-private-ticket>", "expires_in": 120}
```

Wrong, expired, or already consumed codes all return `400 {"detail": "Invalid or expired code."}`. Inactive accounts return `403`. Never send a login ticket to logs or issue trackers; it is a credential even though not a JWT.

## Storage & limits

- Mobile numbers normalize to `+989XXXXXXXXX`.
- Redis key names include keyed SHA-256 digests rather than phone/IP text.
- An OTP is six digits generated by `secrets.randbelow`; its Redis value is an HMAC digest, never the clear text.
- OTP lifetime: **300 seconds**. Maximum **5 incorrect attempts per challenge**.
- Request cooldown: **60 seconds**. Request limit: **3 per phone/hour**, **20 per IP/hour**.
- Verification limit: **15 per phone/hour**, **50 per IP/hour**.
- Successful verify consumes the challenge atomically using Redis `WATCH/MULTI/EXEC`.
- Login ticket: random value, **120-second TTL**, stored only by SHA-256 digest, consumed atomically with `GETDEL` by the next phase.
- Redis downtime fails closed (`503`), not success.

The current rate limiting uses a simple per-key fixed one-hour window. It is intended for this development stage, not a complete production anti-abuse solution. IP determination uses `REMOTE_ADDR`; a future trusted reverse-proxy configuration is required for deployment.

## Local delivery adapter

The only implemented sender is `local_file` and it refuses to run unless Django `DEBUG=True`. It appends JSON lines with codes to **`backend/.otp-outbox`**. The outbox is ignored by Git and contains sensitive credentials. Delete it when finished testing. Never upload or copy it to a ticket, a commit, a screenshot, or a log.

This local adapter is **not an SMS provider**. Production delivery is intentionally disabled until a real provider and operational controls are configured. OTP delivery is synchronous for now; queueing/retries and Celery are separate work.

## Important limitations

- No JWT, token rotation, refresh, or logout yet.
- No SMS service; code only works locally or with a mocked adapter in tests.
- No distributed SMS retry/queue/outbox transaction for delivery yet.
- Abuse prevention also needs device/reputation controls and monitoring before launch.
- Successful OTP creates/verifies a User account only after code verification.
- Existing inactive accounts remain inactive.
- The login ticket must be exchanged and rechecked for active status in the JWT phase.

## Testing

Automated API tests use fakeredis and a stubbed sender, so they don't need external SMS credentials. CI separately checks connectivity to the Redis service. Run:

```powershell
python -m pytest -c backend/pytest.ini backend/tests -v
python -m ruff check backend
python backend/manage.py spectacular --validate --fail-on-warn
```
